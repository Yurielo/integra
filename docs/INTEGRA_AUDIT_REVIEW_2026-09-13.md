# Перепроверка результатов аудита Integra

Дата: 2026-09-13. Объект: `INTEGRA_PROJECT_AUDIT_2026-09-13.md` и
`SOURCE_CAPABILITY_INTEGRATION_MATRIX.md`. Это поправки к оценке, не новая
приёмка приложения. Исходный отчёт сохранён, код не изменялся.

## Вердикт

Основной вывод подтверждён: существуют реальные функции и реальные пробелы;
наличие source-кода, контрактов и успешных тестов не означает доступность
всего сценария в установленном Integra. Однако отчёт нельзя использовать
как полное доказательство пользовательской готовности: доказательства
не привязаны к каждой строке, а несколько оценок смешивают разные требования.

## Существенные выводы, которые подтверждаются

- Source-first registry помечает review/evidence/knowledge неготовыми, хотя
  отдельные действия доступны в результатах. Это разрыв полного маршрута,
  а не основание считать отсутствующим любой backend этих функций.
- В `HEAD:integra_core/user_media.py:311–317` обработка тем завершает задание
  до ветки burn. В рабочей копии ранний выход устранён; регрессия названа
  `test_mixed_topics_and_real_burn_both_execute`. Исправление не равно доставке.
- Ветка `codex/issue-129-source-capability-integration` содержит незакоммиченные
  изменения. Их нельзя учитывать как уже полученные пользователем функции.
- Отсутствие полного Knowledge Studio и полного сквозного маршрута не
  компенсируется статусом принятия отдельных контрактов.

## Исправленный порядок дальнейшей работы

1. До заявления о готовности зафиксировать доказательства по функциям:
   требование → компонент/production entrypoint → действие UI → тест и его
   тип → commit/пакет → bundle smoke → ограничения. Не подменять статусы
   контрактов статусами пользовательских функций и не менять продуктовую политику.
2. Завершить проверку и доставку уже начатого #129 без новых расширений.
   Обязательны три отдельных native/bundle smoke: машинный Evidence,
   VideoText media и реальный OCR выбора/исключения страниц. Проверять реальные
   файлы, выбранные страницы, provenance и отсутствие ложного успеха.
   Полный suite, build, CI и diff-review обязательны; число «581+» само по себе
   не критерий качества. Не пропускать требуемые интеграционные проверки
   из-за отсутствия runtime и затем объявлять их успешными.
3. Надёжность: комбинации outputs, reuse по hash/config/model, отмена без
   оставшихся дочерних процессов и ложного COMPLETED, восстановление после сбоя.
   ASR проверять на разрешённых эталонных примерах; пороги качества фиксировать
   до оценки, а не выбирать по полученным результатам.
4. Замкнуть обязательное ядро: темы → review → знания → точный источник →
   читаемые результаты → Obsidian/файловый OneDrive. Удобный перевод TXT/SRT
   включить сюда, не откладывать за всеми необязательными медиаэффектами.
5. Затем отдельными ограниченными задачами расширять проекты/источники,
   Media Studio и BookText. Не переносить автоматически все возможности
   source-продуктов: для каждой нужна связь с задачами Integra.
6. Marketing/Learning/Assistant/social и переносимость на другие Mac учитывать
   отдельно от текущего ядра. Реальные внешние публикации и принятие знаний
   не являются техническими smoke и не выполняются автоматически.

  Число 581 относится к предыдущему прогону, не к этой перепроверке.

  приложения, commit/push/merge не выполнялось. Текущий remote/CI заново не аттестован.
